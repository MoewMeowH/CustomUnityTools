## 1. 지적 목록

### A1-01
- **위치:** 계획서 Watch 구조 25–26행
- **문제:** [추론] 키별 대기 맵과 메인 스레드의 대기 명령 제거만으로는 최신 호출 순서를 보장하지 못한다. 명령 생성·등록·인출·적용 사이의 원자성 또는 버전 비교가 빠졌다.
- **발생 조건:** 워커의 이전 명령이 등록 직전 정지 → 메인에서 `Unwatch`가 대기 맵을 비우고 삭제 → 워커가 이전 명령을 등록 → 다음 처리에서 부활. 워커끼리도 먼저 시작한 호출이 늦게 등록되어 최신 값을 덮을 수 있다.
- **영향:** 수정 목표인 순서 역전·삭제 후 부활 방지가 성립하지 않는다.
- **심각도:** 높음
- **확신도:** 높음 — 계획의 보장 근거가 부족함
- **검증 방법:** 실행하지 않은 정적 검토. 배리어로 명령 생성·등록 사이를 정지시켜 위 순서를 강제하고 최종 상태와 이벤트 순서를 검사한다.

### A1-02
- **위치:** 계획서 Watch 구조 28–30행 / `HLogCore.cs:565–587`
- **문제:** [사실] 현재 게터는 평가 결과를 무조건 `Watch`로 반영한다. [추론] 목록을 복사하는 수정은 열거 변경만 막으며, 재진입으로 무효화된 게터의 결과 반영은 막지 못한다.
- **발생 조건:** 게터가 자기 키를 `Unwatch`한 뒤 값을 반환하거나, 앞선 게터·이벤트 구독자가 뒤에서 평가할 키를 해제·재등록한다.
- **영향:** 삭제된 Watch 부활, 교체 전 게터 실행, 새 등록값을 이전 평가 결과가 덮는 문제가 남는다.
- **심각도:** 높음
- **확신도:** 높음
- **검증 방법:** 자기 해제 게터, 다른 키 해제 게터, 평가 중 동일 키 재등록을 각각 테스트한다. 삭제 이후 해당 등록 세대의 업데이트 이벤트가 발생하지 않아야 한다.

### A1-03
- **위치:** 계획서 Watch 구조 26행 / B / C 37행 / `HLogCore.cs:131, 629–639`
- **문제:** [사실] 키별 최신 명령 하나는 **동일 키**의 누적만 제한한다. 서로 다른 키 수에는 상한이 없다. 태그를 `RaiseOnMainThread`로 옮겨도 `Action` 큐는 여전히 무제한이며, 로그 처리 상한은 이 큐에 적용되지 않는다.
- **발생 조건:** 워커가 매번 다른 Watch 키나 채널 이름을 생성하거나, 처리 중에도 계속 새 태그를 등록한다.
- **영향:** 대기 메모리·채널 캐시·태그 버튼 증가와 한 프레임의 장시간 처리. “큐 무한 증가 없음”이라는 계획의 결론은 일반적으로 성립하지 않는다.
- **심각도:** 높음
- **확신도:** 높음
- **검증 방법:** 고정 키 반복과 고유 키 반복 부하를 분리해 대기 개수·메모리·프레임 처리 시간을 측정한다. 로그뿐 아니라 태그·Watch 명령에도 처리 예산이 적용되는지 확인한다.

## 2. 사양 확인이 필요한 항목

- **릴리즈 로그 범위:** `LogChannel.Error/Exception`의 Unity 로그 출력도 제거할 것인가? “릴리즈에서 동작 코드 제거”를 모든 HLog 동작에 적용한다면 생성자·프로퍼티·로그 메서드까지 비활성 구현이 필요하다. Resources 포함 여부와는 별개다.
- **Watch 순서 정의:** 겹치는 호출은 어떤 시점을 기준으로 정렬하는가? 호출 시작 시각보다 명시된 접수 시점을 선형화 지점으로 삼는 편이 구현·검증하기 쉽다.
- **Watch 병합 의미:** 워커의 중간값을 버리면 에디터 Watch 트리거도 그 값을 관찰하지 못한다. 임계값을 잠깐 넘었다 돌아오는 경우 트리거 누락을 허용하는가?
- **값·게터 전환:** 게터 등록 후 같은 키에 값 Watch를 호출하면 게터를 교체하는가, 다음 폴링 전까지만 값을 덮는가? 현재 의미를 유지할지 확인이 필요하다.
- **공개 API 스레드 계약:** `Clear`, `IsLogEnabled`, `Initialize`, `Shutdown`, `PollWatchGetters`는 메인 스레드 전용인가? 로그·Get·Watch의 스레드 허용과 구분해 명시해야 한다.
- **자원 상한:** 고유 Watch·태그·채널 수 제한과 초과 시 거절·삭제 정책은 무엇인가? 제한하지 않는다면 무제한 증가 가능성을 문서화해야 한다.
- **종료 의미:** `Shutdown`이 로그 수집만 멈추는지, Watch 평가와 대기 명령 처리도 멈추는지 확인이 필요하다.
- **자동 생성 1회 범위:** 동일 개발 환경당 1회인지, 저장소를 공유하는 모든 환경을 통틀어 프로젝트당 1회인지 확인이 필요하다.
- **호환성 확인:** **자료 부족: 생성 코드 템플릿 전체, 기존 생성 파일 표본, asmdef·package.json, 외부 탭 구현 전체.** 공개 API와 UPM 소비 프로젝트의 컴파일 호환성은 첨부만으로 확정할 수 없다.

## 3. 수정 방향

- **A1-01·02:** 모든 Watch 명령에 명시적 접수 순서를 부여한다. 짧은 공통 잠금으로 접수·키별 병합을 직렬화하거나, 버전 비교가 있는 명령 처리로 구성한다. `Unwatch` 이후 오래된 명령이 살아나지 않도록 제거 버전을 유지한다. 게터는 평가 전후 등록 세대가 같은지 검사하며, 사용자 게터·이벤트는 잠금 밖에서 실행한다.
- **A1-03:** 로그·Watch·태그에 각각 개수 또는 시간 처리 예산을 둔다. 고유 키 제한은 사양 확정 후 적용한다. 태그 전달은 무제한 캡처 `Action` 큐보다 전용 데이터 구조로 분리한다.
- **A1-04:** `UNITY_EDITOR || DEVELOPMENT_BUILD`에 따라 실제 구현과 비활성 구현을 분리한다. 공개 타입·시그니처는 유지하되 릴리즈의 생성·검색·등록·게터 평가 경로를 모두 차단한다. `Instance`·`EnsureUIInstance`는 `null`, 상태·성공 여부 API는 비활성 계약에 맞는 값을 반환하도록 정한다.
- **A1-05:** 메인 전용 API는 계약과 검사를 추가한다. 워커 허용 API라면 상태 변경과 이벤트를 메인 명령 처리로 통합한다. `Clear`가 대기 로그도 버리는지는 별도 확정한다.
- **A1-06:** 예외 태그를 로그 수신 시 `PendingLog`에 복사한다. 태그 범위는 `try/finally`로 이전 값을 복원하고 적용 대상을 제한한다. 콜백 동기 실행 가정이 검증되지 않으면 해당 방식으로 확정하지 않는다.
- **A1-07·08:** 닫힘·초기화·패널 재로드 모두 같은 로그 표시 정책을 사용한다. 메모리 회수가 목표라면 닫을 때 행과 선택 참조를 해제한다. 재바인딩 전에는 반드시 **이전 요소와 이전 델리게이트**로 콜백을 해제한다.
- **A1-09:** 코어 초기화에 대한 캐시 무효화 경로를 명시한다. 전체 상태 리셋 알림 또는 플레이 상태 전환 시 창의 전체 재구성 중 하나로 통일한다.
- **A1-10:** 저장소 전체 기준 1회라면 버전 관리 가능한 비-YAML 마커를 사용한다. 현재 환경 기준이면 EditorPrefs를 유지하되 보장 범위를 고친다. 완료 기록은 기존 파일 확인 또는 생성 성공 후에만 남긴다.
- **A1-11:** 게터 평가·값 변환·이벤트 전달의 예외 경계를 분리한다. 구독자별 실패 격리를 채택한다면 오류 보고가 다시 같은 로그 이벤트로 재귀 진입하지 않도록 보호한다.
- **A1-12:** 초기화·종료·재초기화의 상태 전이와 프레임당 처리 게이트를 정의한다. 테스트 계획을 최종 결정에 맞춰 비개발 빌드의 직접 API·씬 배치·기존 생성 코드 호출까지 확장한다.

## 4. 설계 방향 판단

**수정 후 진행** — 메인 스레드 소유 Watch·링 버퍼·지연 UI 생성 방향은 유지하되, 명령 순서 보장과 재진입 무효화, 릴리즈 전체 진입점 차단을 먼저 설계에 반영해야 한다.

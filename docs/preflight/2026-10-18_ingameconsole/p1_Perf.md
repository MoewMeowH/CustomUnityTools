## 2. 사양에 따라 달라지는 항목

- **처리 예산:** 워커 로그만 제한할지, Watch·태그 이벤트까지 제한할지 결정이 필요하다. 개수 제한은 실행 시간의 상한이 아니다. 임의의 게터 하나가 오래 걸리는 경우는 게터 사이의 예산 검사로도 중단할 수 없다.
- **중간 이벤트 보존:** Watch 최신값 병합은 UI 비용을 줄이지만, 에디터 조건 트리거가 중간 값까지 관찰해야 하는지는 자료 부족: 트리거의 이벤트 보존 요구사항. 처리 병합·표시 지연을 트리거 검사 생략으로 확장해서는 안 된다.
- **규모:** 자료 부족: 최대 Watch·게터 수, 초당 로그 수, 메시지·스택 길이, 고유 태그·채널 수. 이 값에 따라 PF1-02~04의 심각도가 달라진다.
- **플랫폼·열기 반응:** 자료 부족: 최소 대상 모바일 기기와 허용할 콘솔 열기 지연. PF1-06의 일괄 생성 유지 여부는 대상 기기에서 판단해야 한다.
- **릴리즈 호출 비용:** 결정 2의 동작 코드 제거 방향은 맞다. 다만 빈 공개 API도 호출 인수의 문자열 보간·박싱·람다 생성을 막지는 않는다. 자료 부족: 릴리즈에서 호출되는 사용자 코드와 `USE_HLOG` 설정. 이 비용까지 제거할 필요가 있다면 호출 지점의 조건부 컴파일 정책을 별도로 확인해야 한다.
- **제외된 UI:** 자료 부족: FPS 그래프·외부 탭·설정 탭 구현. 닫힌 상태의 매 프레임 비용과 외부 뷰 수명은 제공 범위만으로 판단할 수 없다.

## 3. 수정 방향

- **PF1-01:** 모든 배출 진입점이 공유하는 프레임별 예산을 코어에 둔다. 로그 수집·트리거 검사와 UI 반영을 분리하고, 버튼 개수·일반 표시 갱신은 프레임당 한 번으로 합친다. 메인 스레드 로그의 즉시 이벤트 의미를 바꾸는 것은 별도 합의가 필요하다.
- **PF1-02:** 대기 Watch의 고유 키 용량·초과 정책을 명시하고, 태그 버튼은 보이는 시점에 지연 생성한다. 태그·채널 자동 퇴출은 기존 API 의미에 영향을 줄 수 있으므로 무조건 적용하지 않는다.
- **PF1-03:** `watchRowMap`에서 해당 키의 행만 제거한다. 대량 초기화가 필요할 때만 전체 재구성하고, 닫힌 동안에는 표시 변경을 dirty 상태로 합친다.
- **PF1-04:** 기본 폴링 의미는 유지하되, 타입별 이전 값 비교 후 문자열 변환하는 내부 경로를 검토한다. 폴링 주기 조절은 트리거 관찰 빈도에 영향을 주므로 선택 사항으로 다룬다.
- **PF1-05:** 초기화·패널 재로드·닫기에도 동일한 지연 생성 규칙을 적용한다. 닫을 때 로그 행과 선택 참조를 해제할지 명시하고, 다시 열 때 코어 이력으로 복원한다.
- **PF1-06:** 가상화 도입 없이 UI 행 관리도 선두 이동 없는 구조로 바꾼다. 측정상 열기 비용이 크면 제한된 행 풀 또는 분할 생성을 사용하되, 표시 순서와 스크롤 동작은 유지한다.
- **PF1-07:** 공개 `Watches`의 독립 스냅샷 계약은 유지하고, 에디터 내부는 변경 버전·dirty 상태에 따라 스냅샷을 재사용한다. 트리거 처리는 표시 캐시와 분리해 기존 관찰 의미를 해치지 않는다.

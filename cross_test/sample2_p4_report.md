## 1. 요구사항과 성공 조건

### 1.1 원래 요청 (`sample2_request.md`)
- 대상: `BoidSystem` (C# 9, Unity 6 / 6000.x, Job System + Burst + NativeArray)
- 증상
  - S1. 에디터에서 **가끔** `InvalidOperationException`
  - S2. 빌드에서는 예외 없이 `cell0` 값이 **실행마다** 다름
  - S3. 씬을 닫을 때 **간헐적** 에러
- 목표: 세 증상의 원인을 구분해 설명하고, 근본 원인을 고치는 수정안을 얻는다.
- 제약: 약 20,000개를 Job 병렬로 처리하는 구조 유지 (메인 스레드 단일 처리로 되돌리는 것은 불가)
- 성공 기준: 증상별 원인 구분, 예외 억제가 아니라 에디터·빌드 양쪽에서 결정적인 결과

### 1.2 Phase 2 이후 확정 사항 (사용자)
| # | 확정 내용 | 설계 영향 |
|---|---|---|
| C1 | 결정성 = 같은 시드, 같은 틱 수에서 같은 결과 | 고정 시드 필요, 고정 시간 단계 불필요 |
| C2 | 프레임 레이트 독립성, 플랫폼 간 비트 동일성은 범위 밖 | `Time.deltaTime` 유지, 미해결 쟁점으로 남김 |
| C3 | 핵심은 병렬 쓰기 경쟁으로 `cellCounts`가 흔들리지 않는 것 | 집계 경쟁 제거가 1순위 |
| C4 | unsafe 코드 금지 | 포인터 + `Interlocked` 방식 탈락 |
| C5 | 미정: 프레임별 집계 vs 누적, 속도 0의 의도, `abs(x) % 1024`의 의도 | 원본 동작 보존 또는 선택 가능하게 |
| C6 | 예외 메시지·스택은 아직 없음 | 증상과 원인의 일대일 대응은 실행 단계에서 확인 |

### 1.3 이 보고서의 성공 조건 해석
- "해결"이 아니라 **"Phase 5 실행 검증에서 통과 여부를 판정할 수 있는 수정 설계 + 테스트 기준"** 을 산출물로 본다.

## 3. 채택·기각한 반박과 이유

### 3.1 채택
| 반박 | 제기 | 대상 | 채택 이유 |

## 4. 수정 설계 방향

### 4.1 공통 골격 (두 최종안이 같고, Claude도 타당하다고 판단)
1. 모든 장기 보관 배열을 `Allocator.Persistent`로 할당 (I-04)
2. `CountJob`을 **청크별 부분 히스토그램(`CountChunksJob`) + 셀별 합산(`ReduceCountsJob`)** 으로 교체 (I-01, C3, C4)
   - 청크 `c`는 `[c*1024, (c+1)*1024)` 구간에만 쓴다. 구간이 겹치지 않으므로 `[NativeDisableParallelForRestriction]`이 안전하다.
   - `ReduceCountsJob`은 실행 인덱스에 해당하는 셀에만 쓴다. 기본 쓰기 제한을 그대로 지킨다.
   - 결과는 스레드 수나 배치 크기와 무관하게 결정적이다 [사실, 정적]. 추가 메모리는 79청크 × 1024 × 4B ≈ 316 KiB.
3. `_handle = X.Schedule(..., _handle)` 체이닝으로 예약이 성공할 때마다 핸들 저장 (I-07)
4. 이동 전 위치를 집계하는 순서 유지 (Count → Reduce → Move)
5. 고정 시드로 초기 위치 생성 (I-03, C1)
6. `count <= 0` 거부, `_initialized` 플래그로 Update와 LateUpdate 차단 (I-08)
7. `OnDestroy`: `_handle.Complete()` 후 `IsCreated`인 배열만 해제 (I-05, I-06)
8. 셀 수식, 속도 0, `Time.deltaTime`, `Debug.Log` 유지 (C2, C5)

측정 방법: 코드 블록 내용만 `.cs`로 저장한 뒤 `awk`(전체 줄), `grep -cv '^\s*$'`(빈 줄 제외), 정규식으로 `struct …: IJobParallelFor|IJob`와 `NativeArray<` 필드 선언을 셈.

### 7.3 입장 이동 요약
| 모델 | P1→P2 변경 | P2→P3 변경 | 상대 영향으로 바뀐 수 | 사용자 확정 사항으로 바뀐 수 |

### 7.5 사람 개입

| # | 시점 | 개입 | 이유 | 계획 여부 |
|---|---|---|---|---|
| 1 | 각 단계 사이 (P1→P2, P2→P3, P3→P4) | 다음 단계 지시문 작성·전달 | 실험 설계상 수동 중계 | 계획됨 |
| 2 | P2 → P3 | 확정 사항 C1~C6 제공 | 사양 결정 (모델이 남긴 사용자 질문에 답) | 계획됨 |
| 3 | P3 1차 | MCP 네트워크 타임아웃을 100초에서 300초로 늘리고 서버 재연결 후 재실행 | P3-A가 100초 제한에서 4회 재시도 모두 실패 (재실행 때는 144초 소요) | **비계획** |
| 4 | P3 재실행 후 | 산출물 파일 선택 (재실행 결과를 기본으로 하고 1차 B는 `_run1`로 보존) | 재실행에서 B도 다시 실행됨 | **비계획** |

지휘자(Claude) 쪽에서 절차를 벗어난 부분도 기록한다.
- P3의 두 run 모두 run_mode 결과 텍스트에서 `< >`가 `&lt; &gt;`로 이스케이프되어 왔다. 그래서 응답 원문은 결과 텍스트가 아니라 서버 로그(`calls.jsonl`의 `response`)에서 저장했다.
- run_mode 결과에는 runId와 토큰 정보가 없어 모든 지표를 서버 로그에서 가져왔다.

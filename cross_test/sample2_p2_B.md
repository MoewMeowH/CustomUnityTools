### 2. 상대 수정안 검토

- **B2-08 (섹션 3-1 기본 난수 초기화 코드의 분포 변경 부작용)**
  - **문제**: [사실] 3-1의 첫 번째 코드 블록(`rng.NextFloat3Direction() * 50f`)은 반지름 50인 구의 **표면(껍질)**에만 개체를 배치함. 원문의 `insideUnitSphere * 50f`(구 내부 균일 분포)와 기하학적 분포가 달라져 `cell0`에 들어가는 개체 수 자체가 변경됨.
  - **발생 조건**: 3-1의 두 번째 대안 코드(`math.pow(rng.NextFloat(), 1f / 3f)`) 대신 첫 번째 기본 코드 블록을 그대로 사용할 때 항상 발생.
  - **영향**: 원래 시뮬레이션의 공간 분포 의도가 왜곡됨.
  - **심각도**: 낮음
  - **대응 방법**: 구 내부 분포를 유지하려면 반드시 3-1 하단에 제시된 세제곱근(`math.pow(..., 1f / 3f)`) 수식을 기본으로 적용해야 함.
  - **검증 절차**: 생성된 위치들의 원점 거리(`math.length(pos)`)가 `50f`로만 고정되는지, `0~50f` 사이에 분포하는지 확인.

- **B2-09 (섹션 3-1, 3-2의 `count` 런타임 변경 시 버퍼 크기 불일치 위험)**
  - **문제**: [추론] `_chunkCount`와 `_partialCounts`가 `Start()` 시점의 `count`를 기준으로 고정 할당되나, `CountChunksJob` 내부에서는 `positions.Length`를 참조함. `count`가 `[SerializeField]`이므로 런타임이나 인스펙터 디버깅 중 값이 바뀌거나 배열 크기가 재조정될 경우 불일치 위험이 있음(단, 현재 제공된 코드 내에서는 재할당 경로가 없음).
  - **발생 조건**: `Start()` 이후 `count` 또는 `_positions` 크기가 변경될 때.
  - **영향**: `_chunkCount` 계산 기준이 흔들릴 경우 `partialCounts` 인덱스 범위 초과 가능성.
  - **심각도**: 낮음
  - **대응 방법**: `CountChunksJob` 스케줄링 시 `_chunkCount` 대신 `(_positions.Length + ChunkSize - 1) / ChunkSize`와 `_partialCounts.Length` 정합성을 기준으로 삼거나 `count`를 런타임 변경 불가로 고정.
  - **검증 절차**: 코드 내 `_positions` 재할당 경로 유무 확인.

- **B2-10 (섹션 3-2 청크 히스토그램 + 리듀스 방식의 실용성 평가)**
  - **평가**: [사실] 새로운 문제를 만들지 않으며 요청 범위 내에 있음. 내 Phase 1(B-01)의 `Interlocked.Increment` 방식은 `unsafe` 컨텍스트 설정이 필요하고 특정 셀(예: 초기 위치가 몰리는 0~50번 셀)에 워커 스레드의 캐시 라인 경합(Contention)이 집중되는 반면, 상대의 `CountChunksJob` + `ReduceCountsJob` 방식은 `unsafe` 설정 없이 컴파일되며 스레드 간 캐시 경합을 완전히 제거하여 실용성과 성능 면에서 더 우수함. (추가 메모리 약 316 KiB는 데스크톱/모바일 환경 모두에서 무시할 수 있는 수준임).

### 3. 내 Phase 1 수정

- **B2-11 (B-01 및 B-05 수정 방향 교체)**
  - **수정 내용**: B-01의 해결책으로 제시했던 `unsafe` + `Interlocked.Increment` 및 B-05의 메인 스레드 `UnsafeUtility.MemClear` 방식을 철회하고, 리뷰 A의 3-2(`CountChunksJob` + `ReduceCountsJob`) 방식으로 대체함.
  - **이유**:
    1. [사실] 초기 위치의 `x` 좌표가 `-50 ~ 50` 범위이므로 전체 1024개 셀 중 0~50번 셀에만 20,000개의 원자적 연산이 집중되어 심각한 CPU 캐시 라인 경합이 발생함.
    2. [사실] 프로젝트 설정에서 `Allow 'unsafe' Code`를 켜지 않아도 되므로 기존 프로젝트 환경과의 호환성이 더 높음.
    3. [사실] `ReduceCountsJob`이 매 프레임 결과를 덮어쓰므로 메인 스레드에서 별도로 `MemClear`를 호출할 필요가 없음.

- **B2-12 (B-04 수정 코드의 수학적 분포 오류 정정)**
  - **수정 내용**: 내 Phase 1의 `Start()` 수정 코드 중 `rng.NextFloat3Direction() * rng.NextFloat(0f, 50f)`를 리뷰 A가 제시한 `rng.NextFloat3Direction() * (50f * math.pow(rng.NextFloat(), 1f / 3f))`로 수정함.
  - **이유**: [사실] 반지름을 선형 난수(`NextFloat(0f, 50f)`)로 곱하면 구의 중심부로 개체 밀도가 쏠리게 되어 원문의 `insideUnitSphere`와 같은 3차원 구 내부 균일 분포가 되지 않음.

- **B2-13 (누락된 예외 방어 로직 A-06, A-07 수용)**
  - **수정 내용**: 내 Phase 1에서 누락했던 Job 스케줄링 단계별 `_handle` 즉시 대입(A-06)과 `Start()`에서의 `count <= 0` 검증(A-07)을 수정안에 추가함.
  - **이유**: [사실] 다단계 Job 스케줄링 중 예외 발생 시 핸들 추적 유실을 막고, 잘못된 인스펙터 입력값으로 인한 런타임 예외를 사전에 차단하기 위함.

### 4. 미해결 쟁점

- **B2-14 (실제 발생한 예외 스택 트레이스 및 패키지 환경 미확인)**: `자료 부족: 에디터 InvalidOperationException 및 씬 종료 시 에러의 전체 메시지·스택 트레이스`. 코드상 확인된 안전성 검사 위반(A-01/B-01), 핸들 미완료 해제(A-05/B-02), `TempJob` 수명 초과(A-04/B-03)가 보고된 증상의 직접적인 원인일 가능성이 매우 높으나, 실제 실행 로그 없이는 다른 외부 요인이 없는지 100% 확정할 수 없음.
- **B2-15 (`_cellCounts`의 집계 사양)**: 매 프레임 현재 위치 기준의 개체 수를 계산하는 것인지, 시뮬레이션 시작 이후의 누적 카운트를 의도한 것인지 사양 확정이 필요함.
- **B2-16 (결정론적 결과의 요구 범위 및 `_velocities` 동작)**: 실행 간 동일한 초기 배치와 프레임 이동까지 요구하는지 여부, 그리고 현재 `0`으로만 초기화된 `_velocities`에 실제 이동 값이 들어갈 때 `Time.deltaTime` 변동에 따른 결과 차이를 허용하는지 사양 확정이 필요함.
